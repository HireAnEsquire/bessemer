# 05 — gc: finding what can be reclaimed, and saying so before doing it

Status: Todo
Type: AFK
Blocked by: 00, 02, 04

## What to build

`bessemer/gc.py` — the scan that decides what old run state is reclaimable. Ports
`collect_gc_items`, `summarize_logs`, `render_gc`, `render_gc_plan`, `cmd_gc`'s
computational half, and the size helpers.

**Blocked by 04** for `_format_table` and the age helpers, which `render_gc` shares — porting
them twice is how two renderers drift into disagreeing about what a table looks like.

## The classes this issue owns

Seven, 30 tests:

`CollectGcItemsTests` (11) · `SummarizeLogsTests` (3) · `RenderGcTests` (4) ·
`RenderGcPlanTests` (2) · `CmdGcTests` (4) · `HumanSizeTests` (4) · `DirSizeTests` (2)

`CollectGcItemsTests` is the largest single class in F2 at eleven tests, which is upstream
saying this is where the edges are.

## This issue deletes nothing

`collect_gc_items` **scans and returns a plan**; `render_gc_plan` shows it. Nothing here
removes a file, and that is the whole shape of the thing: the plan is a value the human can
read before anything acts on it, and F3 owns the acting.

State it in the module docstring, because the name says otherwise. A module called `gc` that
returns a list is a module someone will eventually "finish" by adding the deletion, and the
reason it stops short needs to be written down rather than inferred. It is also why this
issue is portable at all — the thing being scanned (checkouts, logs, locks from real
dispatches) does not exist until F3, but a pure scan over paths is testable now with
fixtures.

`HumanSizeTests` and `DirSizeTests` come here rather than to 04 because gc is what needs
sizes — the status view does not report them.

## Acceptance criteria

- [ ] All 30 tests land, assertions intact, pending falls by 30 — to **zero**, if this is
      the last of 01–05 to run
- [ ] **Nothing in `bessemer/gc.py` deletes, moves, or truncates anything.** Prove it: a
      test asserting the module's AST contains no call to `unlink`, `rmtree`, `remove`,
      `rmdir` or `truncate`. A docstring promising restraint is not a check, and this is the
      module where the difference matters most
- [ ] `bessemer/gc.py` spawns no subprocess; container state arrives as parsed rows from
      issue 04
- [ ] `_format_table` and the age helpers are imported from `bessemer/status.py`, not
      re-implemented. A test asserts there is one definition of each
- [ ] `cmd_gc` splits per decision 5, both destinations recorded
- [ ] **Whatever `cli.py` gains to gather gc's inputs is tested by patching `proc.run`, not
      by patching the gather away.** Issue 04's one blocking finding was exactly this: every
      `CmdStatusTests` patched `_docker_rows` wholesale, so both of its failure-collapse
      arms could be inverted with the whole suite green — the daemon-down case rendered the
      healthy blank. The gather is the one piece of new logic with no upstream oracle, so
      the tests are bessemer's own: one nonzero `Result`, one raised `OSError`, one
      `proc.TimeoutExpired`, each asserting the degraded rendering actually prints. If gc
      reuses `_docker_rows` rather than growing its own gather, say so — that is the better
      outcome, and then there is nothing new to test here
- [ ] **Zero `pending` entries remain in the manifest** once 01–05 have all landed, and the
      check that reports the pending count says so. That is F2's tracer condition alongside
      `bessemer status`, and it is the moment the port is either complete or provably not
- [ ] Report what a gc scan does with a checkout that is currently in use. F3 will run gc
      while dispatches are live, and the answer to that is either in the port source or it
      is a gap F3 inherits
